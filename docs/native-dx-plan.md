# Native DirectX 9Ex / 11 / 12 for the game (plan and survey, 2026-11-11)

Owner's wish (2026-11-11): the DirectX choice on Settings > Enhanced should be DirectX 9 (original), 9Ex, 11 and 12, with the game itself drawing through each, **no compatibility layer** between the game and the API (no DXVK, no Windows' `d3d9on12`). Vlad's list was the same four.

## What exists today

| Choice | State |
|---|---|
| DirectX 9 | the game's own |
| DirectX 9Ex | `[display] d3d9ex` (src/d3dcap.c): Direct3DCreate9Ex and CreateDeviceEx, managed pool turned into default/dynamic. Alt+Tab works. **A `vid_restart` stalls** (the new device is made, the menus never come back); nobody found why. Not in the 32-bit build's tests. |

## What the renderer asks of Direct3D 9 (64-bit exe, Ghidra, `tools/ghidra/RendererSurvey.java`, `VcallSites.java`)

The renderer is not scattered over the exe: the device is a global (rva 0x410fd20) read in 39 functions, and the calls through the device's vtable are made in a few dozen functions. Call sites by method (all code of the exe; a few may be other objects' calls with the same slot offset):

- Draw: `DrawIndexedPrimitive` 33 sites in 24 functions, `DrawPrimitiveUP` 5 sites in 1 function (rva 0x28ce0), `DrawPrimitive` none.
- State: `SetRenderState` 71 sites in 23 functions, `SetSamplerState` 16 in 2 (rva 0x4e940, 0x4f380: a state cache), `SetTexture` 11, `SetScissorRect` 9, `SetViewport` 3, `Clear` 1, `SetRenderTarget` 1, `SetDepthStencilSurface` 1, `StretchRect` 4.
- Shaders and geometry: `SetVertexShader` 3, `SetPixelShader` 3, `SetVertexShaderConstantF` 6 (4 functions), `SetPixelShaderConstantF` 3, `SetStreamSource` 18, `SetIndices` 13, `SetVertexDeclaration` 7, `CreateVertexShader` 2, `CreatePixelShader` 2.
- Resources: `CreateTexture` 7, `CreateVertexBuffer` 5, `CreateIndexBuffer` 5, `CreateQuery` 3, `CreateDepthStencilSurface` 1, `CreateCubeTexture` 1.
- Device life: `Reset` 2, `Present` 2, `TestCooperativeLevel` 5, `GetBackBuffer` 2.

So the surface is narrow: roughly 25 distinct device methods, a few hundred call sites, concentrated in the renderer's command-buffer code (rva 0x4e000-0x66000) and its device set-up (rva 0x23000-0x2a000, 0xf000-0x12000). Textures, vertex buffers and index buffers are used through their own interface methods (Lock, Unlock, GetSurfaceLevel, ...), not counted above.

## What a native backend has to do

1. **Shaders.** The game ships Direct3D 9 shader model 3 bytecode (vs_3_0 / ps_3_0; the materials of the fastfiles hold it, the HLSL is not available). D3D11 and D3D12 cannot load it. A translator is unavoidable: SM3 tokens -> HLSL text -> `D3DCompile` (d3dcompiler_47.dll, which the mod already uses in src/fsr3.c) -> DXBC (shader model 5.0 for D3D11, 5.1 for D3D12). About 40 opcodes, the register files (c, i, b, v, o, t, s, r, a0, aL), the dcl semantics. Constants: float constant registers c0-c255 map to one constant buffer per stage that `SetVertexShaderConstantF` / `SetPixelShaderConstantF` fill.
2. **State model.** D3D9's loose render states and sampler states become D3D11 state objects (created on demand, cached by a hash of the state words) or a D3D12 pipeline state object per (shaders, vertex layout, blend, depth, raster, render target formats). The renderer's own state cache (0x4e940) is the natural place to hook, so the translation sees one coherent state at each draw.
3. **Resources.** Formats (DXT1/3/5, A8R8G8B8, A16B16G16R16F, R32F, depth formats sampled as textures: D3D9 depth "INTZ" and shadow-map PCF hacks), dynamic buffers (D3D9 Lock with DISCARD/NOOVERWRITE -> D3D11 map flags or D3D12 upload ring), vertex declarations -> input layouts, render-target textures and multisample resolve (`StretchRect`), occlusion queries.
4. **Swap chain.** DXGI flip model, windowed/borderless, `Present`, resize; the game's own `vid_restart` / `Reset` paths.
5. **Everything the mod does on the D3D9 device today.** The native split screen's compositor, the console overlay, screenshots (src/shot.c), the sunwait/aspect hooks, FSR 3 / DLSS, font atlas filtering: all of it uses `IDirect3DDevice9` calls on the game's device (native.c, console.c, shot.c, fsr3.c, d3dcap.c). A native D3D11/12 backend has to give these a device to talk to, or they must be rewritten against the new backend. This is the biggest hidden cost: native.c alone is about 9000 lines.

## Honest options

- **A. A device object that the game's renderer calls (the backend implements the ~25 methods, resources and the shader translator).** Technically this is what DXVK or d3d9on12 are, made part of the mod and fed by the call sites we know; "native" only in the sense that nothing outside the mod sits between the game and Direct3D 11/12. It keeps the mod's own D3D9-using features working if the backend also exposes the methods they use. Estimate: D3D11 first (state objects, simple resources): several weeks of focused work for a first image, months for fidelity (shadows, sunlit effects, split screen, FSR 3); D3D12 on top of the same translator: weeks more (PSO cache, descriptors, barriers, upload ring).
- **B. Rewrite the renderer's back end (the command-buffer functions at 0x4e000-0x66000) against D3D11/12 without any D3D9-shaped object.** Cleaner and faster in the end, but every game structure the back end reads (GfxCmdBufState, material and technique data, GfxBuffers) has to be reverse engineered, and the mod's features still need their own path. Months.
- **C. Keep Windows' layer for DirectX 12 and add D3D11On12 for 11** (hours to days each): works today, but it is a compatibility layer, which the owner does not want.

## Order of work

1. **DirectX 9Ex first** (native in the sense of the owner's wish, nothing new to write beyond a bug): find why a `vid_restart` stalls on an Ex device and fix it; then put it on the Settings > Enhanced row as an option (not before: it stalls the game when the video options are applied). Leads: the game calls `TestCooperativeLevel` (5 sites) and `Reset` (2 sites); on an Ex device `TestCooperativeLevel` never says `DEVICENOTRESET` and `Reset` is not the Ex call (`ResetEx`); a new device made while the old one is still referenced (our d3dcap keeps the device pointer, the console overlay and native.c hold state blocks and textures on it).
2. **A shader translator (SM3 -> HLSL) with a test that translates the shaders of every material of a loaded level and compiles them** (no game run needed, only the zone data in memory). This is the piece every D3D11/12 path needs, and it can be validated offline.
3. **A D3D11 backend for the world pass** behind a switch, first on the Trainer, then the mod's features.
4. **D3D12** on the same translator.

## 9Ex: what was found on 2026-11-11 (the `vid_restart` stall)

Reproduced in a test copy (`d3d9ex=1`, console `vid_restart` in the main menu, 1280x720 windowed). The game makes the new device (`CreateDeviceEx` succeeds, the render states are set), the window's dark title bar is applied, and then nothing: no Present, no log lines from the menus or the console, no font re-import. Without 9Ex the same `vid_restart` goes on to re-import the fonts and the menus come back within a second. Sometimes the process ends by itself a few seconds later (exit code 0).

- The main thread is inside the device set-up function (rva 0x10550, the one that sets the render states) -> 0xf3f0, which calls the zone loader `DB_LoadXAssets` (rva 0xf0ae0, the call is the sync one) and sits in its `Sleep(1)` loop waiting for the loader's flags (0x140a8a830 / 0x140a8a834) to clear. So the zone reload after the restart never finishes.
- A thread inside `d3d9.dll+0x2c43b` (called from the game's thread start code, no game frames above it) waits in the runtime; the window procedure thread, the overlay thread (gameoverlayrenderer64) and others are idle.
- Not yet known: where the loader's thread is. `crash.c`'s stack dump now prints `module+offset` for frames in other modules (d3d9.dll, the driver), so the next dump shows what each thread waits in. Suspects: a `CreateTexture` / `CreateVertexBuffer` of the loader going through our default-pool conversion and waiting on the device lock held by a Present of the new (hidden) window; or a state the Ex runtime keeps for the old device.

### 9Ex update (later on 2026-11-11): the first cause is found and fixed, the next failure is one step further

- **Found:** the stall was the game's own fatal error. The loader's thread called `Create2DTexture` (rva 0x23950) and the exit stack of the process (exe+0x23a6d -> 0x1fb74a, the error function -> exit) shows it failed. After a `vid_restart` the new Ex device's CreateTexture / CreateVertexBuffer / ... vtable slots were the **original** d3d9.dll entries, not our hooks (the log line added in `hook_resource_creation`: slot 00007FFDE244E310 against our hook 00007FFD599C3350): a managed-pool texture on an Ex device fails. `hook_resource_creation` only ever ran for the first device. **Fix:** it now checks every new device and hooks again when the slot is not ours (src/d3dcap.c, uncommitted). With it the zone reload after the restart goes on (the log reaches the 1000th converted texture).
- **Next failure:** the game still ends at the first or second restart, black: the engine's `Failed init after: Tried to use 'feedbackSampler' when it isn't valid` (reported by the owner, 2026-11-11). The message is printed by the sampler binding code (rva 0x53d00) when the image behind a code sampler is null; `feedbackSampler` is code sampler 8 (the table is set up in rva 0x45930; its image pointer starts at 0 and is set when the feedback effect runs). Why a material that needs it is drawn with it null after a restart on an Ex device is not known: leads are a race with the render thread during the re-init (Present on an Ex device does not block the way a plain device's does) and an image whose creation was skipped.
- Tools added: `tools/ghidra/FindString.java` (a string and its referencing functions), a failed-creation log in the d3d9ex hooks, `module+offset` frames in the stack dump.

### 9Ex status at the end of 2026-11-11

A `vid_restart` on 9Ex works once, like the plain device. A second restart ends the game with the `feedbackSampler` error on both (checked with the mod's restart preparations switched off, `MW2COOP_VIDPLAIN=1`): the engine's own failure; the error is raised on the render thread and on the main thread while the renderer is set up again, in the sampler binding (rva 0x53d00) for a material that needs the feedback image (code sampler 8, its image pointer is never set after the table is cleared in rva 0x45930). ### Step 2 started: the shader translator (`tools/sm3_to_hlsl.py`)

- **Dump:** `MW2COOP_DUMPSHADERS=1` makes the game's device write every vertex and pixel shader it is given (the bytecode of the materials) to `<game dir>\mw2coop\shaderss_<hash>.bin` / `ps_<hash>.bin` (src/d3dcap.c, QA only; the files are the game's data and stay in the test copy). The main menu and the Trainer give 2730 distinct shaders (244 vertex, 2486 pixel, 11 MB).
- **Translator:** a Python module and CLI: version token, DCL / DEF / DEFI / DEFB, about 50 opcodes (ALU, texld / texldl / texldd with projection and bias, cmp, lit, sincos, dsx / dsy, texkill, if / ifc / else / rep / loop / break, relative constant addressing, the matrix ops), source and result modifiers, vPos / vFace; the output is HLSL for shader model 5. Not translated: call / label subroutines, predication (they raise `Unsupported` and are counted); none occurs in the 2730.
- **Compile check:** `python -I tools/sm3_to_hlsl.py --check <dir>` runs each translation through `D3DCompile` (d3dcompiler_47.dll): **2730 of 2730 compile** (ps_5_0 / vs_5_0). That shows the translations are valid HLSL, not that they compute the same as Direct3D 9.
- **Not done:** the semantic check (run a shader on a Direct3D 9 device and the translation on a Direct3D 11 WARP device with the same constants and compare the numbers; the legacy rules that differ: `mul` 0 * inf = 0, `rcp` / `rsq` of 0, `pow`, `lit`, `exp` / `log`), the shadow-map samplers (a comparison sampler depends on the bound texture), the constant table names (the CTAB comments give them), shaders of more levels (the other zones may use call / label or predication), and the cbuffer layout the backend fills.

### Step 2: the semantic check (`tools/sm3_semantic_check.py`, `tools/sm3check.c`)

For each pixel shader the harness runs the original bytecode on a Direct3D 9 device (the machine's GPU) and the translation on a Direct3D 11 WARP device (software) with the same pixel-shader constants (seeded random; the shader's own `def` constants win), the same interpolants (a vertex shader writes seeded constants to every interpolant), the same textures (2D, cube and volume by the shader's declarations, linear, clamped) and the same render targets (A32B32G32R32F, up to four), and compares the pixel it writes.

- **Interface lesson:** Direct3D 11 links the stages by register; the pixel shader's input structure now always starts with `SV_Position` and the vertex shader's output structure starts with it too. Without that the interpolants were shifted by one (a pixel shader read the position where it wanted a colour).
- **Result on the 2485 pixel shaders of the main menu and the Trainer** (one depth-output shader skipped), noise textures: 1571 match, 506 both write zero, 408 differ; of those 306 by less than 0.02, 76 by 0.02-0.2, 26 more. The differences follow the filtering of the noise (cube face seams are filtered across faces by Direct3D 11 and not by this Direct3D 9 GPU, 8-bit filter weights) and the GPU's approximations of exp / log / pow.
- **Result with `SM3FLAT=1` (every texel of a texture the same, so only the arithmetic is compared): all 2485 agree** (1987 match, 498 both write zero, 0 differ). So the translation computes what Direct3D 9 computes for these shaders: the opcodes, the modifiers, the sampler dispatch (2D, cube, volume, projected, biased, lod), the flow control, the constants (def, relative addressing).
- **Vertex shaders** (`SM3_VS=1 python -I tools/sm3_semantic_check.py <folder>`, `sm3check --vs`): Direct3D 9 runs the original bytecode with `ProcessVertices` on a device with software vertex processing (the runtime's own CPU implementation, exact arithmetic), Direct3D 11 WARP runs the translation with stream output (the vertex shader's bytecode as the geometry shader of a stream-output stage); three vertices of seeded values, the same constants, every output component compared. **All 244 vertex shaders agree.** The check was shown to see errors: with the translation deliberately broken (every ` + ` turned into ` - `) all 30 tried shaders differ.
- **Eight levels** (the Trainer, Roadkill, Cliffhanger, Airport, Favela, Oil Rig, Invasion, Estate and the Endgame wake-up; the plain game, each for about a minute, 2026-11-11): **4120 distinct shaders** (285 vertex, 3835 pixel). All translate and compile; **all 3834 pixel shaders (flat textures: 3178 match, 656 write zeros on both sides) and all 285 vertex shaders agree with Direct3D 9**, none of them uses call / label subroutines or predication, none reads a texture in the vertex stage, one writes depth.
- **Not covered:** the shadow-map comparison samplers (a property of the bound texture), the one depth-output shader, the shaders of the rest of the campaign (the dump is one environment variable away).

Steps 3-4 are not started.

## Decision (2026-11-11, the owner): option B

Rewrite the renderer's back end directly against Direct3D 11 / 12, with no Direct3D 9 shaped object in between. Option A (a fake `IDirect3DDevice9`) and option C (Windows' layers) are off the table.

### The back end, as read from the 64-bit exe (Ghidra, `local/scratch/ghidra/backend1.c`; all numbers are rvas unless stated, **observations**, not yet checked in a running game)

- Every draw function takes a context `{input*, state*}`. `state` is the command-buffer state (GfxCmdBufState): `+0xd0` the device, `+0xd8` the index-buffer cache, `+0xe8` / `+0xf0` / `+0xf8` the stream-source cache (stride, buffer, offset; `SetStreamSource` is skipped when they match), `+0xe0` a mode flag, `+0x120` the material, `+0x128` the technique index, `+0x130` the technique, `+0x138` the current pass.
- A pass (MaterialPass): `+0x18` per-primitive argument count, `+0x19` per-object argument count, `+0x1a` stable argument count, `+0x20` the argument array (16 bytes each, in that order). A draw is always the same sequence: select the pass (`0x54a10`), apply render state (`0x54940`), stable arguments (`0x54070`), vertex stream, per-object arguments including the samplers (`0x53d00`), per-draw constants (`0x53f10`), then `DrawIndexedPrimitive(TRIANGLELIST, 0, 0, numVerts, startIndex, primCount)`. The loop over passes is `0x26840`; the other draw paths (`0x399f0`, `0x5c960`, `0x5cc10`, `0x5e950`, `0x5f220`, `0x5fe50`) are the same sequence for sprites, lights, particles, the sky and so on; `0x50a20`, `0x50ec0`, `0x543b0`, `0x54220`, `0x28ce0` and `0x252e0` set up state and targets.
- So the game already has a **small, regular back end**: a few dozen functions that turn "material + technique + pass + argument list" into device calls. That is what is replaced. The front end (visibility, sorting, building the draw lists, the zone data, the fastfile loader) stays untouched.
- The code samplers (`feedbackSampler` and its siblings, table at input `+0x12c0`) are bound through `0x53d00`; the error "Tried to use 'feedbackSampler' when it isn't valid" comes from that binding when the image pointer of code sampler 8 is NULL (found while looking at the second `vid_restart` after a 9Ex or plain restart).

### What the new back end is made of

1. **Shaders:** `src/dx/sm3.c` (done, below) turns each material's shader bytecode into HLSL; `D3DCompile` makes DXBC; the compiled blobs are cached on disk by a hash of the bytecode so the compile cost is paid once.
2. **Argument binding:** the pass's argument array already says, for every shader constant, where its value comes from (a code constant, a material constant, a sampler). The new back end evaluates the same list but writes into a per-stage constant buffer image (`float4 c[256]`, one `Map(DISCARD)` / upload per draw or per changed range) instead of calling `SetVertexShaderConstantF`.
3. **State:** the render-state words of a pass (blend, depth, cull, alpha test, colour write mask, stencil) become cached D3D11 state objects, or pipeline states on D3D12, keyed by the words.
4. **Resources:** the game creates textures, vertex and index buffers through its own wrappers (`Create2DTexture` 0x23950 and the buffer creators); they are replaced by the new API's resources. Image data reaches them from the loader, not from `Lock`.
5. **Frame:** swap chain (flip model), render targets and the depth buffer, the resolve and the post-effects, then the mod's own overlays (console, split-screen compositor, FSR 3 / DLSS) rewritten against the new device.

### How it is validated: the mirror, then the switch

A rewrite of this size cannot be judged by playing. Each milestone has a check that runs without a human:

- **M1 (done):** shader translator in C, byte-for-byte the same compiled shaders as the Python reference on all 4120 shaders of eight levels (`tools/sm3c_test.c` + `tools/sm3c_compare.py`). The Python version was validated against Direct3D 9 itself (`tools/sm3_semantic_check.py`: 3834 pixel and 285 vertex shaders agree).
- **M2 (mirror):** while the game draws through Direct3D 9 as today, a second D3D11 device receives the same draws, fed from the back-end functions' own data (material, pass, arguments), not from the D3D9 call stream. Check: the D3D11 frame against the D3D9 frame, pixel by pixel, on the QA levels (Trainer first). The mirror is scaffolding; it is deleted at M5.
- **M3 (UI and sprites), M4 (world, lights, particles, sky):** each draw path switched over one at a time, the same frame comparison after each.
- **M5 (switch):** the D3D9 device is no longer created; the mod's overlays move to the new device; the Enhanced page's DirectX row gets the real "DirectX 11" entry.
- **M6:** Direct3D 12 on the same translator, state cache and argument binding (pipeline states, descriptor heaps, an upload ring, barriers).

Not decided yet: whether the 32-bit exe follows (its back end has other rvas; the address resolver of `docs` would need a section for them) and how the split screen's second view is drawn (done in `native.c` on the D3D9 device today; not read for this plan yet).

### The structures the back end reads (64-bit exe; read from the decompiled draw path `0x26840` / `0x54a10` / `0x54940` / `0x54070` / `0x53d00` / `0x53f10` / `0x543b0` / `0x50a20`; field names are ours, taken from what each field does)

**Observed** (every offset below is read by the code above, and the vtable slots match `IDirect3DDevice9`):

- **Context:** `{input*, state*}` (16 bytes, passed by value or pointer). `input` = per-frame data (code constants, code samplers), `state` = GfxCmdBufState.
- **input:** `+0xe00 + i*16` code constant `i` for `i < 0x4c` (a float4 each); derived constants (`i >= 0x4c`) are computed on demand by `0x502f0`; `+0x156c + i*2` / `+0x1674 + ((i-0x4c)>>2)*2` a 16-bit version counter per constant (a constant is re-sent only when the version in the cached `(version << 32 | index)` word of the register differs); `+0x12c0 + k*8` the image for code sampler `k` (NULL means "Tried to use '<name>' when it isn't valid", names at 0x144113618 + k*8), `+0x1398 + k` its sampler-state byte; `+0x16e0` a target mode.
- **state:** `+0x10 + s*4` sampler-state word of sampler `s` (16 samplers), `+0x00 + s` its filter byte, `+0x50 + s*8` the bound image of sampler `s`; `+0x150 + r*8` the cached `(version, index)` word of vertex-shader constant register `r`; `+0x350 + r*8` the same for pixel-shader constants; `+0xd0` device; `+0xd8` index buffer; `+0xe0` vertex type (index into a decl's per-type table); `+0xe8/+0xf0/+0xf8` stream 0 (stride, buffer, offset), `+0x100/+0x108/+0x110` stream 1; `+0x118` current vertex declaration; `+0x120` material; `+0x128` technique type; `+0x130` technique; `+0x138` current pass; `+0x140` pass index; `+0xb54/+0xb58` the two render-state bit words in effect; `+0xb68` current pixel shader; `+0xb70` current vertex shader; `+0xb98` current render target / depth set.
- **Material:** `+0x00` name; `+0x20 + techniqueType` one byte = index of the first state-bits pair for that technique; `+0x58 -> +0x10 -> +0x38` the technique used by the full-screen paths; `+0x60` texture table (16-byte entries: `+0` name hash, `+6` sampler-state byte, `+7` semantic, `+8` image); `+0x68` constant table (32-byte entries: `+0` name hash, `+16` four floats); `+0x70` state-bits table (8 bytes = two 32-bit words, the render-state description of one pass).
- **Technique:** `+0x0a` pass count (16-bit), `+0x10 + p*0x28` pass `p`.
- **Pass (0x28 bytes):** `+0x00` vertex declaration set (`+0x30 + vertexType*8` the Direct3D vertex declaration, 0 = "Vertex type %i doesn't have the information used by shader %s in material %s"), `+0x08` vertex shader (`+0` name, `+8` the Direct3D shader object), `+0x10` pixel shader (`+8` the object), `+0x18` per-primitive argument count, `+0x19` per-object argument count, `+0x1a` stable argument count, `+0x20` the argument array, in that order (per-primitive, per-object, stable).
- **Shader argument (16 bytes):** `+0` type (16-bit), `+2` destination register, `+4..` by type. Types and the code that handles them: 0 material vertex constant (name hash at +8, looked up in the material's constant table, float4 at entry+16, `SetVertexShaderConstantF`), 1 literal vertex constant (pointer at +8), 2 material sampler (name hash at +8, looked up in the texture table; semantic 11 = water, 2/3/5/8 = the "default" images when `DAT_1441135c8` is set), 3 code vertex constant (`+8` index 16-bit, `+10` first row, `+11` row count), 4 code sampler (`+8` index into `input+0x12c0`), 5 code pixel constant (same layout as 3), 6 material pixel constant, 7 literal pixel constant. Only the pixel-constant types are in the stable list; `0x54a10` applies the pixel stable arguments, `0x54070` the vertex stable ones, `0x53d00` the per-object ones, `0x53f10` the per-primitive code vertex constants.
- **Draw:** vertex data goes in through `SetStreamSource` (slot 100 = `0x320/8`), indices through `SetIndices` (`0x340`) from a ring (`0x54820` copies `count*3` 16-bit indices into a dynamic index buffer, `0x54b30` the same for 32-byte vertices), `DrawIndexedPrimitive(TRIANGLELIST, 0, 0, numVerts, startIndex, primCount)`.

**Not yet known:** the render-state bit words' layout (`0x505a0` and `0x50810` turn the two words into `SetRenderState` calls and `0x4f380` turns a sampler word into `SetSamplerState`), the derived constants (`0x502f0`), the render-target / viewport set-up (`0x50ec0`, `0x4e940`), what the vertex types are, and where the images get their Direct3D textures (the loader). Those are the next slices.

**Consequence for the plan:** the data the new back end needs is already in these tables. The translation of one pass is: bind the pass's two shaders, fill two constant buffers from the argument list (the same cached-version logic can stay), bind images for the sampler arguments, derive blend / depth / raster state from the two state-bit words, set the vertex layout from the declaration set for the current vertex type, and draw. The mirror (M2) can hook the same function that applies a pass (`0x54a10` and its four helpers) and issue the Direct3D 11 version of exactly that.

### The render-state words (the two 32-bit words of a pass's state-bits pair; `0x505a0`, `0x50810`, `0x4f510`, `0x4f660`, `0x4f6e0`, `0x4f380`, `0x511d0`; tables read from the exe at rva 0x370328, 0x370900, 0x370920, 0x370980, 0x3708c0, 0x3708e0)

**Observed** (the bit positions are the ones the code tests; the Direct3D 9 render state each one drives is given by its id; the Direct3D 11 column is ours, to be checked):

| Word 0 bits | Direct3D 9 state it sets | Value table | Direct3D 11 |
|---|---|---|---|
| 0-3 | `SRCBLEND` (19) | 0 unused, 1 ZERO, 2 ONE, 3 SRCCOLOR, 4 INVSRCCOLOR, 5 SRCALPHA, 6 INVSRCALPHA, 7 DESTALPHA, 8 INVDESTALPHA, 9 DESTCOLOR, 10 INVDESTCOLOR (the Direct3D 9 numbers) | `SrcBlend` of the render-target blend desc |
| 4-7 | `DESTBLEND` (20) | same | `DestBlend` |
| 8-10 | `BLENDOP` (171) | 1 ADD, 2 SUBTRACT, 3 REVSUBTRACT, 4 MIN, 5 MAX; **0 = blending off** (`ALPHABLENDENABLE` 27 is set 0 when bits 8-10 are 0, else 1) | `BlendOp`, `BlendEnable` |

**Sampler word** (`0x4f380`, one 32-bit word per sampler, built from the material's sampler byte): bits 0-7 anisotropy level (`MAXANISOTROPY` 10, only when 2 or more, else the filters are used), 8-11 `MINFILTER` (6), 12-15 `MAGFILTER` (5), 16-19 `MIPFILTER` (7) (Direct3D 9 values: 0 none, 1 point, 2 linear, 3 anisotropic), 20-21 / 22-23 / 24-25 `ADDRESSU / V / W` (1 wrap, 2 mirror, 3 clamp, 4 border), 26 `SRGBTEXTURE` (11). Direct3D 11 folds all of it into a `SamplerState` object (filter enum, address modes, max anisotropy); the sRGB flag moves to the shader resource view's format.

**Alpha to coverage** (`0x50550`): the code sets a driver-specific render state (id 181, the FourCC `ATOC` or `SSAA`) when multisampling is on and the blend operation is off. Direct3D 11 has `AlphaToCoverageEnable` in the blend desc.

**What this means for the design:** a pass's blend, depth-stencil and rasterizer state are each a pure function of a few bit fields of two words. A Direct3D 11 back end keeps three small hash maps (key: the relevant bits; value: the state object) and never needs the loose render-state model. The one thing without a counterpart is the **alpha test**, which has to move into the pixel shader (a small constant buffer `{alphaFunc, alphaRef}` and a `clip` before the shader's outputs are written; it costs nothing when the function is "always"). The translator's output needs a hook for that: an extra `AlphaTest()` call in front of `return output;`.

### Derived constants, viewport, render targets (`0x502f0`, `0x4feb0`, `0x50ec0`, `0x50ba0`, `0x50c60`, `0x3cc00`, `0x4e940`; static reading, not run)

- **Derived constants are computed on the CPU by the game, lazily and with versions.** A code constant `i >= 0x4c` is a row of a derived 4x4 matrix (4 rows per matrix; `i - 0x4c` selects the row, `(i - 0x4c) >> 2` the matrix). `0x502f0(input, i, firstRow)` returns the pointer to the row's float4s after bringing the matrix up to date: if the 16-bit version of the matrix (`input+0x1674+((i-0x4c)>>2)*2`) differs from the row's (`input+0x156c+i*2`) it recomputes (`0x4feb0` picks the formula by the matrix number: copies of the base matrices, transposes via `0x265920`, 4x4 inverses via `0x264360`, products, a few cases add camera-position offsets) and caches it. **The new back end calls `0x502f0` itself and copies the float4s into its constant buffer**; no matrix math has to be rewritten. The version counters (`+0x156c`, `+0x1674`) are the cache keys: a constant buffer image only needs rewriting for registers whose cached `(version, index)` word changed, exactly as the game does today with `SetVertexShaderConstantF`.
- **Viewport and scissor:** state `+0xb88..+0xb94` the viewport (x, y, width, height), `+0xb78..+0xb84` the scissor origin and size, `+0x148` / `+0x14c` the depth range (min, max; `0x3cc00` flips between two ranges, the "depth hack" used for first-person models). `0x50c60` calls `SetViewport` (slot 47, `0x178/8`) with those six numbers and `SetScissorRect` (slot 75, `0x258/8`). Direct3D 11: `RSSetViewports` and `RSSetScissorRects` with the same values (`MinDepth`, `MaxDepth`); scissor must be enabled in the rasterizer state.
- **Render targets:** `0x50ec0(ctx, n)` switches to render-target set `n` from a table at rva 0x4359000 (32 bytes per entry: `+0x00` the image, `+0x08` the colour surface, `+0x10` the depth surface, `+0x18` / `+0x1c` the size). It first unbinds from every sampler any texture that is the new target, calls `SetRenderTarget(0, colour)` (slot 37) and `SetDepthStencilSurface` (slot 39), clears the cached sRGB-write bit (state 194) when it was set, and takes the viewport size from the entry. The Direct3D 11 equivalent is `OMSetRenderTargets` with views created once per image, and `PSSetShaderResources(NULL)` for the sampler slots that hold the target (Direct3D 11 refuses a resource bound as input and output at the same time, and would silently drop the binding).
- **Per-frame set-up:** `0x4e940` sets the default render and sampler states for all 16 samplers (the per-sampler words it records are at rva 0x4356bd0), and `0x4ec20` the full-screen 2D projection constants (`input+0x13c0..0x1478`, `+0x500`): a pixel-to-clip transform from the viewport size.
- **Still unknown:** stencil reference and mask (`STENCILREF` 57, `STENCILMASK` 58, `STENCILWRITEMASK` 59 are set somewhere in the scene code, not in the per-pass functions); the clear (`Clear` is called by the scene set-up, not found yet); occlusion queries; the code path that creates the textures and surfaces in the table at rva 0x4359000.

### Clear, images, scissor, end of frame (`0x51070`, `0x492d0`, `0x23950`, `0x391d0`, `0x42fd0`, `0x43100`, `0x44d00`, `0x484c0`; static reading, not run)

- **Clear** is one function, `0x51070(device, flags, float4 rgba, depth, stencil)`: the colour is converted from 0..1 floats to bytes (`floor(x * 255 + 0.5)`, clamped to 0..255) and packed, then `Clear(0, NULL, flags, color, depth, stencil)` (slot 43). Direct3D 11: `ClearRenderTargetView` with the floats directly, `ClearDepthStencilView` with the flags mapped (Direct3D 9: 1 target, 2 depth, 4 stencil; the Direct3D 11 clear flags are DEPTH = 1, STENCIL = 2).
- **Images** are created in one place, `0x492d0(image, format-ish, w, h, flags, d3dFormat)`: by the dimension bits of the flags (`flags & 0x30000`: 0 = 2D `0x23950`, 0x10000 = cube `0x23be0`, 0x20000 = volume `0x23a90`, otherwise a 1-pixel-wide 2D texture for 1D) it calls `CreateTexture` (slot 23, `0xb8`) / `CreateCubeTexture` / `CreateVolumeTexture` on the global device (rva 0x410fd20) and stores the texture object at the image's first field. Image fields: `+0x00` the texture object, `+0x08` kind (3 = 2D, 2 = 1D), `+0x18` / `+0x1a` / `+0x1c` width / height / depth, `+0x20` the name. Usage rule (from `0x23950`): if flag bit 25 is set the image is a render target (usage 1), or a depth-stencil (usage 2) when the format is one of the D3D9 depth formats D24S8 (75), D24X8 (77), D16 (80); if bit 26 is set the pool is SYSTEMMEM, otherwise MANAGED for plain textures (usage 0) and DEFAULT for the rest; bit 15 of the flags adds the dynamic usage. After creation `0x48bd0` is called (the data upload / mip set-up, not read yet). On failure the engine error is "Create2DTexture( name, w, h, 0, format ) failed".
- **The depth buffer** the world pass draws into is one shared depth-stencil surface made once by `0x391d0` (`CreateDepthStencilSurface`, width and height from the render-size globals, multisample type from the device parameters) and handed out to every render-target entry that needs a depth surface; it is `AddRef`ed per use. In Direct3D 11 this is a `D3D11_TEXTURE2D` with `D24_UNORM_S8_UINT` (or `R24G8_TYPELESS` with a depth shader-resource view where the shaders sample depth, which the "INTZ"-style hacks of the game need; to check on the dumped shaders which ones sample a depth image).
- **Scissor** for UI clip rectangles comes in as two draw-list commands (`0x42fd0` set, `0x43100` clear): they clamp the rectangle to the current clip bounds, set `SCISSORTESTENABLE` (state 174) and call `SetScissorRect` (slot 75). So scissor is a render state that the Direct3D 11 rasterizer-state cache must key on (one bit: enabled).
- **End of frame** is `0x44d00`: it copies the frame's dynamic vertex data (a list of 32-byte-per-vertex pieces, `count * stride` bytes per piece, from the command buffer area `+0x1730`) into a dynamic vertex buffer with `Lock` (slot 11 of the buffer, flag `0x1000` = NOOVERWRITE) / copy / `Unlock`, then `EndScene` (slot 41). So vertex data of the UI and of all `DrawPrimitiveUP`-style draws goes through **one per-frame upload**, which suits a single `Map(WRITE_DISCARD)` in Direct3D 11. `0x484c0` is the scene composite: it renders the world into the off-screen targets, then `StretchRect` (slot 34, `0x110`) copies between surfaces (four such call sites in total: `0x3ea40`, `0x41160`, `0x484c0`, `0x5c240`; Direct3D 11: `CopyResource` / `CopySubresourceRegion` when sizes and formats match, a full-screen draw when they do not).
- **Still unknown:** the stencil reference and masks (`STENCILREF` 57 etc.; the tool listing of the 23 functions that call `SetRenderState` was cut off after 12 names, so the rest are unread), occlusion queries (3 sites, all in `0xf760`), the vertex-buffer and index-buffer creators' flags (`0xf760`, `0x24d00`, `0x24fa0`, `0x24df0`, `0x252e0`, `0x2aec00`, `0x2af9c0`), the data upload `0x48bd0`.

### M2, first piece: the state decoder, checked against the game (2026-11-11)

### The oracle, second round (2026-11-12, Trainer, 1280x720, plain game; Steam works again)

Findings that the real back end must honour too (each one was a visible error in the replay, found by comparing with the Direct3D 9 picture; **measured**, not yet re-checked on other levels):

1. **Upload through `UpdateTexture`** (device slot 31): the Bink film planes (`0x2b7840` / `0x2b7980`) and the model-lighting textures (`0x2a0a0`, `r_altModelLightingUpdate`) are written into system-memory textures (`LockRect` with flags 0x10 / 0x8000, then `AddDirtyRect`) and copied to the real texture by `UpdateTexture`. The film was solid green before the copy was replayed (mean difference 99% → about 15%; the rest is the video advancing between two captures). Direct3D 11: `UpdateSubresource` or a staging texture + `CopyResource` per update; the film planes are `L8` (Y 1280x720, Cr / Cb 640x360) and need a single-channel format (`R8_UNORM`; the mirror widens them to 8888, the real one should not).
2. **Cube and volume textures are used by the world**: sky, reflections and the 256x256 colour volume (`kind 3`, A8R8G8B8). `LockRect(face, level)` on cubes (slot 19) and `LockBox(level)` on volumes (slot 19) are the upload paths (`0x49170`, `0x48fa0`); `LockBox` is always called without a box. Direct3D 11: `TextureCube` (array of 6, `MiscFlags TEXTURECUBE`, subresource = face * levels + level, same face order) and `Texture3D`.
3. **Surface objects are transient**: the game calls `GetSurfaceLevel` again and again (`0x484c0`: 11096 times per run), and a released surface's address comes back for a surface of another texture. Anything that maps surfaces to textures must rewrite the entry on every `GetSurfaceLevel` (the mirror had kept the first mapping; texture locks through stale surfaces went to the wrong texture, the "odd texture lock" log lines).
4. **Integer vertex inputs**: `D3DDECLTYPE_UBYTE4` (texture coordinates and normals packed as bytes, usage 5 and 3) reaches a Direct3D 9 vertex shader as floats 0..255; the Direct3D 11 format `R8G8B8A8_UINT` delivers integers and a shader that declares the input `float4` reads the bits as a float. The result was flat-coloured, unlit-looking models and ground (the silhouettes in the first replay). Fix: the vertex shader declares such an input `uint4` (`UBYTE4`) or `int4` (`SHORT2` / `SHORT4`) and converts it with `float4(...)` (`sm3_translate_vs`, `sm3_int_input`); the compiled vertex shader depends on the declaration it is used with, so the shader cache key is (shader, set of integer elements). A shader used with a declaration that types an input differently is compiled again.
5. **`CreateRenderTarget`** (device slot 28) with the fourcc `NULL` (`0x4c4c554e`) is the depth-only render target trick of the shadow-map passes (1024x2048 and 512x2048); one 1280x720 A8R8G8B8 surface is a plain target. Direct3D 11: depth-only draws have no render target view (`OMSetRenderTargets(0, NULL, dsv)`); the mirror allocates a colour texture instead. Skipped draws for "no render target" went from 20% to 0.
6. **`StretchRect` equal sizes** copies the scene to a texture (`0x484c0`); the copy needs the back buffer to be a known 8888 resource. No scaled `StretchRect` was seen in this run.

Result after 1 to 6 on the Trainer start: the world frame (camo net, ground, soldiers with texture and shading, sky with clouds, shadows, HUD text) is drawn by Direct3D 11 and looks like the Direct3D 9 frame; 99.9% of the draws are replayed (186356 of 186577 by frame 1440), 0 shader, layout or texture failures.

**Open, measured:** (a) the full-screen fade quad at the end of the frame (a 1x1 opaque black `$black` image, alpha-blended with the vertex colour's alpha, `c6ffe40f` pixel shader (hash of its bytecode), the same one the text uses) is not black in the Direct3D 11 picture while it covers the Direct3D 9 picture completely during the level's intro fade; cause not found (the texel, blend states and bound texture are right in the trace). (b) The replay runs at about 1 frame per second in the 3D world (all uploads through `UpdateSubresource` of whole shadows, state-object lookups), fine for a QA oracle, not an indication of the real back end's speed. (c) EndScene is called more than once per frame (scene count is not the frame count): the oracle compares at every 120th `EndScene`, which is sometimes an empty scene right after the presented one.

Debug aids added to the oracle (QA only): `MW2COOP_MIRRORTRACE=<scene>` logs the last 120 draws of a scene (blend state, render target, shaders by hash, first texture and its first texel, the first pixel-shader constants); the per-frame skip line counts bound textures that were never uploaded and texture locks / unlocks.

### The flush half on Direct3D 11 exists (2026-11-12): `src/dx/natdraw11.c` / `.h`, test `tools/natdraw_test.c`

`nd` takes what natgfx collected (the two constant register files with dirty bits, shaders, vertex declaration, images and sampler words, the two render-state words) and what the draw functions set directly (render target / depth images, viewport, scissor, stencil reference and masks, vertex streams, index buffer) and makes the Direct3D 11 draw: a `state11_decode` of the words into cached blend, depth-stencil and rasterizer objects (keyed by the decoded fields; the alpha channel's blend factors lose the colour-factor forms as Direct3D 11 demands; polygon offset comes from a callback that is the game's `0x511d0`), cached sampler objects from the sampler words (the sRGB bit goes to the view), input layouts from the declaration (the game's `D3DVERTEXELEMENT9` list as `nd_elem`), shader variants compiled on first use per vertex declaration (integer inputs, `sm3_int_input`), the constant buffers (b0 = 256 float4, b1 = integer / boolean constants, zeros: nothing in the pass lists sets them; b2 = the alpha-test triple from the words) and one `DrawIndexed`. An input image that is the current render target is not bound (the rule found by natcheck). What the first runs taught (each a fix in the code):
1. **Device start (`natbring.c`) must do what 0x10550 does after the device exists**: `0xf3f0` (requests the common zones: `$white`, the default images), `r_rendererInUse` dvar = 0 (every shader of source version 0 is skipped otherwise), the pool tables, `0xf570`, the render-target table, the rings and queries. A 64-bit `__try` does not exist in MinGW clang: diagnostics use `nbr_dump_threads` and `RtlCaptureStackBackTrace`.
2. **Engine code that was not rewritten calls methods on pointers it stored.** The native objects start with a Direct3D 9 style vtable where such a call is known: buffers (Lock +0x58, Unlock +0x60, Release +0x10: static buffers made at Unlock, staged skinned-vertex rings synced to the GPU before a draw reads them, dynamic buffers by Map / Unmap), queries (Issue +0x30, GetData +0x38), shaders, declarations and images (Release; images count references because the render-target table's entries release their "surfaces" like Direct3D 9 does). The window table's swap chain slot holds a stub with a Release. Pattern when a new one shows up: an access violation at a tiny or garbage address in a hooked path; the VEH log line gives the caller's rva.
3. **Image creators have more callers than 0x492d0** (the asset loader 0x23db0 and a function table): 0x23950 / 0x23a90 / 0x23be0 are replaced themselves. The film planes need `BinkGetRects(bink, 0)` from `bink2w64.dll` (green without it). Model lighting: a block's address is RowPitch * y + 16 * x and 0x1fa40 takes its destination in rdx (the decompiler hid it).
4. **Function pointers of the draw code (`ngf`) are set at hook install and must survive `nbr_start`**; losing them left meshes without index buffers and made 0x45d40's loop spin on a cursor that never advanced.
5. **Hardware shadow maps**: Direct3D 9's `tex2Dproj` on a depth texture returns the comparison; Direct3D 11 returns the depth. The pixel shader is translated per set of depth-bound samplers (`SM3_SHADOW_MASK`, `Texture2D<float>` + `SampleCmpLevelZero` with a comparison sampler, linear = PCF); with `sm_enable 0` the picture was right, with them wrong, which found it.
6. **Bridge for the functions not rewritten yet** (0x60120, 0x62890 .. 0x659a0, 0x642e0, 0x64980, 0x64e80, ...): `patch_sites()` turns their `call [reg + slot * 8]` instructions of SetRenderState / SetTexture / SetScissorRect / DrawIndexedPrimitive / SetStreamSource / SetIndices (rva 0x40000 .. 0x66000, 6 and 7 byte forms) into `call rel32` to stubs that jump to native steps with the same arguments. No Direct3D 9 object is involved; a function rewritten natively stops using its sites. SetRenderState maps only state 174 (scissor test enable); every other state logs once "not mapped yet" (none appeared in the Trainer run). **This is a decision for the owner**: it is not the pure rewrite he chose.
7. **Mod users**: the fonts atlas patch is off (it read Direct3D 9 texture objects), `!shot` saves the native frame (`natboot_shot`), the console panel is drawn over the frame (`console_native_frame` + `nd_overlay`, alpha blit; no cursor sprite yet). Off with the native renderer: FSR 1 / FSR 3 / DLSS, `d3d9ex`, `d3d9on12`, the split screen compositor, `d3dcap` features (`[display] directx11` makes settings.c ignore those keys).

Not done: `TestCooperativeLevel` / device lost (removed device), exclusive full screen and alt-tab not tested, gamma in windowed mode, alpha-to-coverage, vertex textures, `0x484c0` / `0x5c240` post-process paths seen only at the Trainer's start, split screen, upscalers, the rest of the campaign (only Trainer and the menus ran), 32-bit build (native renderer is 64-bit), **Direct3D 12 (not started)**.

### The Direct3D 12 back end (2026-11-12): `src/dx/nat12.c`, `natdraw12.c`, `nat12x.h`

The abstraction the plan made at the start (only `nat11.c` and `natdraw11.c` touch Direct3D 11; everything else calls the `nat_*` / `nd_*` API) held: Direct3D 12 is the same two headers with other `.c` files. `tools/natdraw_generic_test.c` (backend neutral: pixels read through `nat_read_pixel`) passes on both: `natdraw11 + nat11` and `natdraw12 + nat12` (build line: `clang -Isrc/dx tools/natdraw_generic_test.c src/dx/natdraw12.c src/dx/nat12.c src/dx/natgfx.c src/dx/state11.c src/dx/sm3.c -ld3d12 -ldxgi -ldxguid -luuid -lole32`).

Design: one direct queue and one command list (render thread), three command allocators (frames in flight), flip-model swap chain of three buffers, a fence value per submission (`pending`). Images stay in COMMON (plain textures are promoted implicitly by the first read); render targets and depth images have tracked states and are transitioned by `nat12_image_transition`. Texture uploads (`nat_image_upload`, called by the asset loader thread) go through a copy queue, synchronously. Buffers live in upload heaps (static ones are cut from 32 MB chunks; rings rotate versions on DISCARD / Lock). Per-frame rings: 96 MB of constants (a draw uploads its dirty constant register files, 4 KB each, into it: a frame of more than about 8000 draws flushes and waits), 333k shader-visible descriptors (a 16-entry table per distinct set of images), sampler tables cached per distinct set of 16 (the sampler heap holds 2048). One root signature: root CBVs b0 / b1 (vertex stage), b3 / b4 / b5 (pixel stage: SM3_D3D12 moves the translator's pixel constant buffers there), an SRV table t0..t15 and a sampler table s0..s15. Pipeline state objects are cached by (shaders, declaration, blend / depth / raster state words, target formats, samples); the first use of each costs a compile on the render thread. Event queries are fence values, occlusion queries a query heap resolved at the end of the list; `nat_save_scene_bmp` and `nat_read_pixel` flush and wait. The queue is also the swap chain's.

In one DLL: `build.sh` compiles the renderer files that call the API (and the two Direct3D 12 files) a second time, prefixes every global symbol they define with `b12_` (`llvm-objcopy --redefine-syms`) and links both; `natboot.c` (Direct3D 11) hands over to `b12_natboot_install` when `[display] directx12=1` (or `MW2COOP_NATIVE12=1`). The DirectX row of the Enhanced page has "DirectX 12 (native)" as its fifth choice.

Not known yet: whether the game runs on it (the first in-game run is the next step), the cost of pipeline state compiles and per-draw constant uploads, MSAA resolves at present, exclusive full screen with the flip model.

## Features on the native renderers (2026-11-12 night)

All in the DirectX 11 and 12 back ends; settings.ini `[display]` (documented in content/release/settings.ini):

- **Flip model swap chain, tearing, frame latency**: `natswap.h`. 11 and 12 use `FLIP_DISCARD`, the frame latency waitable object (`lowlatency=1` queues one frame instead of two) and present with `ALLOW_TEARING` when vsync is off, the window is not in exclusive full screen and the system allows it.
- **`aniso=2|4|8|16`**: forces anisotropic filtering on every sampler that is mipmapped with linear min/mag (`nd_aniso_override`; the game's own level stays when it asks for more).
- **`hdr=1`** (`hdr_white`, `hdr_peak`): scRGB swap chain (R16G16B16A16_FLOAT, G10 P709) when Windows has HDR on for the monitor; the scene is linearised (gamma 2.2), scaled to the paper white, highlights stretched towards the peak, in a final pass. The buffers go half float BEFORE `CheckColorSpaceSupport` (it asks for the current format). `MW2COOP_HDRFORCE=1` forces it on an SDR monitor (looks overexposed there, by design).
- **`upscale=1`** (FSR 1, `upscale_width/height/sharpness`): the scene stays at the game's size, the swap chain and the window have the output size (`upscale_native_sizes`, `upscale_device_made` from upscale.c); EASU + RCAS are the SM3 shaders of upscale.c turned into SM5 by text substitution (`natup.h`). Final passes: scene -> EASU -> RCAS -> (HDR) -> back buffer, `pass11` / `pass12`. FSR 3 / DLSS: see below (native Direct3D 12 only; ignored on DirectX 11 and lower, where `upscale=1` is the upscaler).
- **Shader cache**: `natcache.h`, compiled DXBC on disk in `mw2coop/shadercache`, worker threads warm it when the game loads its shaders.
- **Bug found with it: a render target change must reset the viewport and scissor** (Direct3D 9 does; the engine's blur / downsample passes rely on it). Without it the pause blur and every effect that renders into a smaller target came out as one flat colour (the owner's "solid colour flash"). `ngf_target_switch` in natdrawfn.c.
- QA: `MW2COOP_FRAMETIME=1` (frame times, shader compile times), `MW2COOP_TRACEFRAME=<n>` (every draw of one frame), `MW2COOP_DUMPBACK=<n>[,<n>..]` (the picture of those presents as `mw2coop/native11/back-<n>.bmp`, 11 and 12; with an upscaler it is the output-size picture with the 2D).
- **Split screen** (mode 10) on the native renderers: `natboot.c` compositor (`cp_*`): each half is a scene image with its own 2D layer (premultiplied overlay, `nd_overlay_premul`, alpha rule `state11_layer_fix`), depth-tested 2D draws are rerouted to the scene, paired presents (`natframe_skip_present`), the cg aspect comes from the scene size. Scope lens scissor and title lines are ported (`ng_scissor_hook`, `native_nat_titles_wanted`).
- **`modtex.c`**: the mod's own textures (logo, pad icons and glyphs, fonts) behind one interface that makes a D3D9 texture or a native image (`natboot_tex_*`, `nat_image_download` for reading back).
- **Bink films**: `natfilm.h` fits the draws of the movie planes to the movie's shape (letterbox / pillarbox) because the D3D9 path stretched with its own viewport.
- **FSR 1 and the HUD**: the 2D passes draw into the output-size image at output resolution (`nd_hud_scale` scales viewport and scissor) so text stays crisp.
- **FSR 3 (`natfsr3.c`, Direct3D 12 only)**: `ng_draw_hook` injects the jitter into the world matrix before the constant upload, a readable copy of the depth (R32F pass), camera motion vectors from the previous view-projection, then the motion refinement of src/fsr3.c ported (same two compute passes, `fsr3_refine` 0/1/2, previous picture copied each frame): moving objects and the weapon get vectors of their own; seen in the Roadkill weapon, where the speckled ghosting around the gun is gone (QA: `FSR3_NOREFINE=1`, `FSR3_RFSWITCH=<upscaled frame>` turns it on in mid run for a same-run comparison), the FFX dispatch on the renderer's own command list, output sharpened by RCAS and used as the image the HUD is drawn on. Needs the AMD loader and upscaler DLLs (`fsr3_dir`, see settings.ini). MSAA is switched off while it runs (FSR 3 anti-aliases itself).
- **DLSS (`dlss=1`)**: the same passes, evaluated through `mw2coop_dlss.dll` (`src/dlss`, NVIDIA's SDK is not in the repo). **Not tested: no NVIDIA files or GPU on the dev machine.** A failure falls back to the plain picture with a log line.
- **MSAA / alpha to coverage**: `msaa=0|1|2|4|8` overrides the game's anti-aliasing setting (lowered to what the card supports), `atoc=1` draws alpha-tested things (foliage, fences, hair) with alpha to coverage into multisampled targets (`st.a2c`, an alpha-test constant in the pixel shader). MSAA scene images are resolved when read as a texture and as the stretch source of the final passes.
- **Enhanced page rows** for msaa, aniso, hdr, lowlatency (the row distance shrinks to fit `PAGE_H`); `atoc` is in settings.ini only.
- **Texture LOD bias** with FSR 3 / DLSS: the world pass's mipmapped samplers get AMD's log2(render / output) - 1 (`nd_lod_bias`, set in natfsr3.c setup; settings `fsr3_lodbias` overrides; the 2D passes are excluded because they draw while `nd_hud_scale` is set; sampler cache key includes it).
- **Open**: split-screen dedupe and perf diagnostics, Alt+Tab, DLSS on real hardware.
